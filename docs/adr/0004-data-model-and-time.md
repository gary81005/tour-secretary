# 0004 資料模型與時間

- 狀態：已採用（2026-11-04）；M1 實作細節補充於 2026-11-06；M1 需求訪談紀錄補充於 2026-11-19

## 背景

使用者實際的行程表（`docs/samples/東北秘境探險.xlsx`）大多寫模糊時段（上午／中午／下午／晚上），一個項目常包含多個地點，並且寫了不少備案與旅伴限制。

## 決策

- 結構：**Trip → Day → Item**；名詞定義見 `CONTEXT.md`。
- **Item** 必填 TimeSlot（清晨／上午／中午／下午／傍晚／晚上／整天），選填開始／結束時間；必填 Category（景點、餐食、交通、住宿、購物、提醒）。
- Item 對應 **0 到多個有序 Place**；M1／M2 只存文字，M3 才解析成地圖地點。
- 正式結構：**Stay**（住宿）、**TripNote**（提醒事項）、**Fallback**（掛在 Item 下的備案）、**TravelerConstraint**（旅伴限制）。
- 延後：候選住宿比價、預算記帳。
- **時間存當地時間 + IANA 時區**（時區放在 Day），畫面一律顯示當地時間。

## 理由

- 行程的本質是「當地幾點在哪裡」；存 UTC 再依裝置換算，出發前與抵達後看到的時間會不同。
- 只有填了精確時間的 Item 才觸發落後提醒，避免模糊時段造成誤報。
- Fallback 與 TravelerConstraint 是臨時調整（M6）與 AI 提案（M7）最重要的輸入。

## M1 實作細節

資料表見 `supabase/migrations/`；純邏輯在 `src/lib/trip/`（有測試）。

### 天與日期

- `days` 一天一筆，以 `(trip_id, date)` 唯一；「第 N 天」是依日期排序的序號，不存資料庫。唯一鍵是 `deferrable`，整趟平移時可以一次改完所有日期。
- `days.timezone` 為 null 表示沿用 `trips.default_timezone`；時區名稱由 trigger 驗證。
- 一趟行程最多 60 天（`trips_date_range`）。
- 起訖日與天的日期**不能直接改**，只能透過四個 RPC，天數才不會和日期範圍脫節（Q15）：
  - `shift_trip`：整趟平移到新的出發日，每天的內容跟著第 N 天移動；平移天數在函式內用當下的出發日計算。
  - `set_trip_dates`：修改起訖日，以日期對應；要刪的天還有項目時整筆擋下，並回傳那些日期。
  - `insert_day_after` / `delete_day`：之後的日期往後／往前移一天。
- 平移、插入一天、刪除一天時，住宿日期跟著天一起調整；只住被刪那一晚的住宿改成軟刪除。
- `set_trip_dates` **不調整住宿**：縮短範圍後，範圍外的住宿保留原日期，住宿分頁標示「不在行程日期內」（Q23：範圍外只提醒），由使用者自己改或刪。

### 時段與排序

- 時段的預設時間範圍：清晨 05–08、上午 08–11、中午 11–14、下午 14–17、傍晚 17–19、晚上 19–24，「整天」排最前（`src/lib/trip/time-slot.ts`）。
- 填了開始時間自動帶入時段，使用者可以改回來；00:00–05:00 歸到清晨。不支援跨午夜（結束時間要晚於開始時間）。
- 同一天依時段排序；同時段內，有精確時間的排前面並照時間排，沒有時間的照 `position`（手動順序）。
- 只有沒填時間的項目可以拖拉；拖到別的時段就改成那個時段（`reorder_items`）。

### 項目、地點、備案

- `save_item` 在同一個 transaction 寫入項目，並整批替換它的地點與備案；新項目或換了天／時段的項目排到該時段最後。
- 地點與備案沒有軟刪除，隨項目一起存。
- 連結只接受 http(s)：資料庫 check constraint + 顯示前的 `isSafeHttpUrl()`。

### 軟刪除（Q13、Q14）

- 有 `deleted_at`：`trips`（進垃圾桶）、`items`、`stays`、`trip_notes`、`traveler_constraints`（刪除後提示框可以「復原」）。
- 超過 30 天由 `pg_cron` 每天執行 `purge_deleted_rows()` 永久刪除。
- 沒有軟刪除：`days`（刪除前確認）、`item_places`、`fallbacks`（隨項目存）、`trip_members`。
- 天被刪除時（`delete_day`、`set_trip_dates`），那一天**已經軟刪除**的項目會隨著天一起永久刪除，不再能復原；未刪除的項目會先擋下（`set_trip_dates`）或在確認對話框提醒（`delete_day`）。

## M1 需求訪談（2026-11-05）

M1 開工前逐題確認的決定。程式碼與 migration 的註解用「ADR 0004 Q22」引用這裡的題號；其他 ADR 的 Q 編號是各自 milestone 的訪談，題號彼此無關。訪談之後改過的，寫在「後來」。

- **Q1 Email 登入**：同一封信同時有連結與 6 位數驗證碼。PWA 裡點連結常會開到外部瀏覽器，驗證碼可以直接在 App 裡輸入。實作見 ADR 0005「M1 實作細節」。
- **Q2 要登入的頁面**：除了登入相關的頁面都要登入；`/` 就是行程列表，沒有產品介紹頁。
- **Q3 使用者名稱**：M1 先建 `profiles` 表，由 trigger 帶入登入方式提供的名稱與頭像，不提供編輯。後來：M5 加了「我的名稱」；沒有名稱時顯示「旅伴」，不用 Email 前半段（ADR 0005）。
- **Q4 行程日期與天**：設定起訖日，系統自動產生每一天。整趟延後時，內容跟著「第 N 天」移動。
- **Q5 時區**：行程有預設時區，每一天可以個別改。選單是常用的亞洲時區，最下面的「其他時區…」可以搜尋完整清單；建立行程時預設 `Asia/Tokyo`。
- **Q6 時段與排序**：時間範圍與排序規則見上方「時段與排序」。
- **Q7 項目欄位**：必填標題、時段、類別；選填開始／結束時間、說明、連結、地點（0 到多個，有順序）、備案。備案分成「觸發條件」（選填）與「替代方案」兩欄，M6、M7 才能判斷哪個狀況該套用哪個備案。
- **Q8 住宿**：欄位有名稱、入住日、退房日、地址或地點、訂房狀態（候選／已預訂／已付款）、確認碼、訂房連結、備註。住宿獨立一個分頁，單日畫面最下方顯示依日期推算的「今晚住」；住宿不另外存成行程項目。
- **Q9 提醒事項與旅伴限制**：提醒事項是「主題＋內容」；旅伴限制是「類型（飲食、體力、行動、偏好、其他）＋內容」，另有選填的「對象」。
- **Q10 行程頁排版**：頂部四個分頁「行程、住宿、提醒、限制」。行程分頁上方是可以橫向捲動的天數列，下面只顯示選中的那一天。
- **Q11 資料讀寫**：讀取在 Server Component，寫入用 Server Actions 加 zod 驗證，寫完重新讀取頁面資料；權限由 RLS 與伺服器端把關。後來：表單都改用 `useFormSubmit`，不用 `useActionState`，驗證失敗時使用者的輸入才不會被清空。
- **Q12 成員表與刪除**：`trip_members` M1 就建，建立行程時把建立者加為主辦人，RLS 一律用「是不是成員」判斷。刪除採軟刪除，細節見 Q13、Q14。
- **Q13 軟刪除的範圍**：只有整趟行程進垃圾桶；項目、住宿、提醒事項、旅伴限制刪除後，畫面下方顯示「已刪除・復原」提示。後來：已刪除的資料不在 RLS 過濾，否則「復原」無法 update，見上方「軟刪除」。
- **Q14 垃圾桶**：30 天後由 `pg_cron` 自動永久刪除，垃圾桶顯示「還有 N 天永久刪除」。提前永久刪除要輸入行程名稱確認。
- **Q15 修改日期**：分成「整趟平移」（天數不變，內容跟著第 N 天）與「修改起訖日」（以日期對應，要刪的天有項目就擋下）。每一天另有「在後面插入一天」與「刪除這一天」，有項目時先確認。
- **Q16 編輯畫面**：手機從底部滑出接近全高的面板，桌機是置中的對話框；關掉後停在原本的捲動位置。表單裡可以改「第幾天」，把項目移到別天。
- **Q17 手動排序的方式**：直接做拖拉（`@dnd-kit`），不先做「上移／下移」。規則見 Q22。
- **Q18 單日畫面的分組**：依時段分組，只顯示有項目的時段。底部一個「新增項目」按鈕，新增時預設最後一組的時段。
- **Q19 時間與時段不一致**：填了開始時間就自動帶入對應的時段，使用者可以改回來。不支援跨午夜，結束時間要晚於開始時間。
- **Q20 行程列表**：分成「進行中、即將出發、已結束」三組，卡片顯示名稱、日期、天數、城市，不放封面圖。「今天」依每一天的時區判斷，不看手機的時區。
- **Q21 建立行程**：只填名稱、起訖日、預設時區，建好直接進第 1 天。城市在單日畫面再填，可以一次套用到之後連續幾天。
- **Q22 拖拉與精確時間**：有精確時間的項目不能拖，位置由時間決定，把手的位置顯示時鐘；沒填時間的可以拖，拖到別的時段組就改成那個時段。只能從把手拖，才不會和捲動衝突。換天用 Q16 的表單，不做跨天拖拉。
- **Q23 提醒事項與住宿的排序**：提醒事項可以拖拉排序，住宿依入住日排序。住宿的入住到退房要在行程日期內，退房日可以是最後一天；日期重疊只提醒，不阻擋。
- **Q24 開發用的資料庫**：只用雲端的 Supabase 專案。migration 要能重複執行，push 前先給使用者看 SQL。後來：M5 加了用 Docker Postgres 跑的 SQL 回歸測試（`npm run db:test`）。
- **Q25 登入信**：M1 先用 Supabase 內建的寄信服務，信件範本放在 `supabase/templates/`。後來：M5 仍然沒有接自己的 SMTP（ADR 0005 Q5），列在 roadmap。
- **Q26 直接照建議做的細節**：
  1. 登入頁：上面是 Google，下面輸入 Email；寄出後切換成輸入驗證碼，並提示也可以點信中的連結。
  2. 登出在右上角的頭像選單。
  3. 行程設定在行程頁右上角的「⋯」選單。
  4. 垃圾桶從頭像選單進入。
  5. 每個類別一個固定的 lucide 圖示，只用主題色，不另外加顏色。
  6. 「已刪除・復原」用 sonner 的提示框。
  7. 桌機版內容置中、最寬 `max-w-2xl`，不做雙欄。
  8. 測試只測純邏輯。
